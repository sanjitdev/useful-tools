### Patterns We Noticed

Amelia (Developer): "Speaking of patterns, I noticed something when reviewing the 12 story records..."

Amelia (Developer): "Five of the seven MUST-FIX findings from the post-epic review were about drift — drift between spec and script, drift between doc and manifest, drift between count and count, drift between harness and what-it-tests. That's a single theme: **the project has many sources of truth and they don't auto-sync.**"

Sanjit (Project Lead): "Right. We have `tools.json` (35 entries), `tools.schema.json` (the contract), `docs/tool-inventory.md` (the inventory doc), `docs/quality-audit.md` (the per-tool audit), `docs/pack-taxonomy.md` (the pack roster), the `WAVE_N_*` constants in the promotion scripts, the api-contract.js manifest, the smoke harnesses, the regression sweep, the `_audit_wave_*.py` outputs, and the `_es5_grep.py` scan. That's ten+ canonical sources. Any pair can drift."

Charlie (Senior Dev): "The mitigation is generation, not discipline. `docs/shell-public-api.md` §5 should be generated from `api-contract.js`. `docs/quality-audit.md` should be generated from the audit scripts. `docs/tool-inventory.md` should be generated from `tools.json` + `tools/`. When the doc is the derivative, drift becomes impossible."

Dana (QA Engineer): "And the negative-test battery is the same shape. The sweep's checks are the derivative of the broken-fixture assertions. When a check is missing, the negative test fires. When a check is wrong, the negative test fires. The relationship is enforced by the test infrastructure, not by the maintainer."

Amelia (Developer): "Right. So the unifying pattern is: **derive secondary artifacts from canonical ones; verify the derivation with negative tests.** That's a general principle, not just a one-off fix."

Amelia (Developer): "Second pattern — the wave-3 count drift surfaced a class of bug we hadn't formalized. Counters and identities that appear in multiple files need a single source. The 33-vs-35 was a count drift. The 16-vs-17 was another. The 35 ready:true vs 33 spec was a third. The fix is to either generate the count from a single source (e.g., count ready:true in `tools.json`) or to assert agreement between the count and a known truth in CI."

Sanjit (Project Lead): "I like the second one. The CI assertion is cheaper than the generation. We can add a check: 'count of ready:true entries in tools.json must equal the count asserted in the regression sweep summary.' If they ever diverge, the build fails."

Amelia (Developer): "Yes. And the third pattern — the synthetic DOM in Story 2.12 grew by 13 helper additions across the development cycle. That's the 'failure-driven harness improvement, not tool-specific hacks' pattern from the Epic 1 retro, applied at a larger scale. The key insight is that the synthetic DOM is a *compatibility layer* for our test environment, not a tool-specific shim. When a tool needs a browser API, the layer gains it. The cost is the layer's complexity; the benefit is that no real tool needs a special case."

Elena (Junior Dev): "I want to add the wave-3 spec drift to the count pattern. The spec said 16. The implementation promoted 17. The spec wasn't updated. That's a workflow gap: when a story's scope changes during implementation, the spec should change too. The story doc has a 'Tasks/Subtasks' section — we should have a 'Spec Change Log' that captures scope changes."

Sanjit (Project Lead): "Good idea. Story 2.10 had a 'Spec Change Log' in its spec. Story 2.12 didn't. The diff is discipline, not infrastructure."

**Patterns identified:**

1. **Drift across multiple sources of truth is the dominant bug class.** Manifest ↔ runtime, doc ↔ manifest, spec ↔ script, count ↔ count. Mitigation: generate secondary artifacts from canonical ones; add CI assertions for cross-source agreement.
2. **Negative tests are the meta-test.** Any inventory-style sweep or count-asserting harness needs a broken-fixture test that proves the check fires. The 6/6 caught pattern in `scripts/_smoke_regression_sweep_negative.js` is the template.
3. **The synthetic DOM is a compatibility layer, not a tool shim.** When a tool needs a browser API, the layer gains it. The cost is layer complexity; the benefit is zero tool-specific exceptions.
4. **Counter/identity drift across files needs CI assertions.** 33-vs-35, 16-vs-17 — same shape. Add a check: 'count of ready:true in tools.json must equal the count asserted in the regression sweep summary.'
5. **Spec change logs are part of the workflow.** When a story's scope changes during implementation, the spec should be updated alongside the code. Story 2.10 had it; Story 2.12 didn't. The gap is discipline, not tooling.
