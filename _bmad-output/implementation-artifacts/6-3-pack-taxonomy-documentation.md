# Story 6.3: Pack Taxonomy Documentation

## User Story

As a future contributor adding a tool to a pack,
I want `docs/pack-taxonomy.md` to define each pack's inclusion criteria with concrete examples and out-of-pack counters,
So that the taxonomy is explicit, self-checking, and not vibes-based.

## Current State (post Story 2.9)

- `docs/pack-taxonomy.md` exists, auto-generated by `scripts/_pack_tags.py` on every `make pack-tags` run. The current doc lists each pack with a one-line purpose and a tool roster (35 tools / 37 pack-slots / 5 packs ≥ 3 tools).
- The doc's "Inclusion Criteria" section is a single bullet per pack (one-line). Story 6.3 expands this to **3–5 bullets per pack** with **2 in-pack examples** (already implicit in the roster) and **2 out-of-pack examples with reason** per pack.
- `make pack-tags` regenerates the doc; `make pack-tags-smoke` is the Node-side defense (every `ready:true` entry has a valid pack array). Both run in `make ci`.
- Schema-level pack enum enforcement (`tools.schema.json`) is the third defense layer.
- `CONTRIBUTING.md` does **not** exist in the repo (verified 2026-08-12). Story 6.3 introduces it with a `## Pack taxonomy` section linking to the taxonomy doc.
- PRD Open Q1 ("Travel vs. Household split") is unresolved. Story 6.3 resolves it as part of writing the taxonomy.

## Acceptance Criteria

### AC-1 — Enriched pack taxonomy doc

**Given** a maintainer wants to know which pack to assign a new tool to
**When** they read `docs/pack-taxonomy.md`
**Then** the file lists each of the five packs (`travel`, `finance`, `study`, `developer`, `household`) with: a one-line purpose, **3–5 bullet inclusion criteria** (a tool lands in the pack iff ≥ 1 criterion matches its primary use case), **2 in-pack example slugs** (already in `tools.json` for the pack), and **2 out-of-pack example slugs with a one-line reason** (a real slug from `tools.json` that lives in a different pack, plus a hypothetical such as `currency-converter` or `paint-calculator` from the Epic 6 backlog)
**And** the resolved definition for **Travel vs. Household** is recorded at the top of the doc per AI-3: **Travel = mobility / timezone / currency / on-the-road logistics; Household = domestic / area / volume / recipe / at-home life math** (PRD Open Q1)
**And** the doc's tool rosters and pack counts remain mechanically generated (no manual drift; `scripts/_pack_tags.py` is the source of truth)
**And** the example slugs in the new bullets are present in `tools.json` today (the in-pack examples) or are flagged as "Epic 6 backlog" (the hypothetical out-of-pack examples) — never invented.

### AC-2 — `scripts/check-pack-taxonomy.py` CI gate

**Given** a maintainer adds a new tool or changes an existing tool's pack assignment
**When** they run `make ci`
**Then** a new step `make check-pack-taxonomy` runs `scripts/check-pack-taxonomy.py`, which:
  - reads `tools.json`,
  - finds any `ready:true` entry whose `pack` field is missing or not in the allowlist `{travel, finance, study, developer, household}`,
  - **does NOT fail on missing pack alone** (the schema already enforces presence); it **posts a CI comment suggestion** using a hand-rolled **keyword-to-pack map** (`scripts/check-pack-taxonomy.py:KEYWORD_TO_PACK`) that maps lowercase substrings of the tool's `category` + `keywords` fields to a recommended pack,
  - exits **0** when every tool's pack is valid (the script's job is a *suggestion*, not a gate — the schema is the gate),
  - exits **2** on repo-layout issues (schema, tools.json, or wave-promo script missing),
  - exits **3** on I/O failure
**And** the suggestion output is line-per-tool with the format `  <slug>: pack=<current>; suggested=<guessed> (matched: "<keyword>")` so a reviewer can spot-check the recommendations
**And** the script is **idempotent and pure-stdlib Python** (no third-party deps), matching the project's CI conventions.

### AC-3 — `make check-pack-taxonomy` is wired into `make ci`

**Given** `scripts/check-pack-taxonomy.py` exists
**When** the maintainer runs `make ci`
**Then** `check-pack-taxonomy` runs as one step in the chain (after `pack-tags-smoke`, before `wave-1-smoke` — the natural order is: schema → python pack auditor → node pack smoke → taxonomy comment)
**And** the Makefile's `help` text lists the new target with a one-line description
**And** `.github/workflows/tool-contract-gate.yml` gains a `make check-pack-taxonomy` step with path filters covering `scripts/check-pack-taxonomy.py`, `tools.json`, `tools.schema.json`, and the Makefile.

### AC-4 — `CONTRIBUTING.md` ## Pack taxonomy section

**Given** a new contributor reads `CONTRIBUTING.md`
**When** they reach the `## Pack taxonomy` section
**Then** it links to `docs/pack-taxonomy.md` ("See [docs/pack-taxonomy.md](docs/pack-taxonomy.md) for the full criteria, in-pack examples, and out-of-pack examples for each of the five packs.")
**And** it **quotes the inclusion criteria verbatim** for each of the five packs (the bullets from the taxonomy doc), so a contributor can read them without leaving `CONTRIBUTING.md`
**And** `CONTRIBUTING.md` is a new file at the repo root with at minimum the `## Pack taxonomy` section; additional sections (e.g., `## Setup`, `## Adding a new tool`) are out of scope for this story — Story 6.3 introduces the file and ships the one section.

## Resolved Open Questions

### PRD Open Q1 — Travel vs. Household split (resolved 2026-08-12 per AI-3)

The PRD flagged potential overlap. Story 6.3 adopts the **orthogonal definitions** proposed in PRD §8:

| Pack | Definition | Example tools (today) |
|---|---|---|
| `travel` | **Mobility / timezone / currency / on-the-road logistics.** The primary user is in transit or coordinating across timezones. | `countdown-to-date`, `date-difference`, `world-clock` |
| `household` | **Domestic / area / volume / recipe / at-home life math.** The primary user is at home managing personal-life tasks. | `bmi-calculator`, `calorie-estimator`, `habit-tracker`, `eisenhower-matrix` |

**Decision rule for ambiguous tools**: if the tool's primary use case has the user *physically away from home* (e.g., "I'm in Bangkok and want to call my team in Berlin"), it is `travel`. If the primary use case has the user *at home or in their local context* (e.g., "I'm planning next week's meals"), it is `household`. Currency conversion is `travel` (away from home base); budgeting the household grocery bill is `household` (in-place). Paint / area / volume calculators land in `household` (Epic 6 backlog).

This resolves the open question with a clear, defensible rule. No tool in the current 35 needs to be re-tagged.

### Implementation Plan

1. Author the per-pack inclusion bullets + examples first (T1) — this is the editorial heart of the story and gates T2/T3/T5.
2. Extend `_pack_tags.py` (T2). The new constants are colocated with the existing `WAVE_*_PACKS` import. The doc emitter gains a new section per pack: `### Inclusion criteria` + `### In-pack examples` + `### Out-of-pack examples (and why)` + the existing roster.
3. Write `check-pack-taxonomy.py` (T3). Pure stdlib (`json`, `argparse`, `sys`, `pathlib`). Same shape as `_pack_tags.py` (constants up top, idempotent run, vacuous-pass guard, exit-code conventions).
4. Wire Makefile + CI (T4). Pattern matches the existing `pack-tags` + `pack-tags-smoke` pair.
5. Write `CONTRIBUTING.md` (T5). Minimal file. The verbatim bullets are copied from the new `_pack_tags.py` constants at author time.
6. Regression sweep (T6). All Node smokes + Python gates must remain green.

### Known limitations

- `CONTRIBUTING.md`'s verbatim bullets are copied at author time and are not auto-synced with `docs/pack-taxonomy.md` on regeneration. A drift-check would be a `check-pack-taxonomy` extension in a follow-up story if drift becomes a recurring problem. Story 6.3 ships the simple version.
- `KEYWORD_TO_PACK` is hand-rolled, not learned. This is intentional: a learned model would silently change recommendations on every run, violating the "explicit, not vibes-based" AC. The hand-rolled map is auditable in PR review.
- Story 6.3 does not add per-tool-category-to-pack tagging. The keyword map operates on `category` + `keywords` substrings, which is enough for today's 35 tools and the Epic 6 backlog.
