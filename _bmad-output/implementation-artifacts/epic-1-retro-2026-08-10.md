Elena (Junior Dev): "Right. So — I read the commit history. Story 1.14 shipped as commit `16cfba7`, and then a second commit `2631cb3` came in titled 'review fixes: 4 MUST-FIX'. Four must-fix items in a single story. That's... a lot of 'must-fix' for a story that was supposed to be done."

Amelia (Developer): *intervening calmly* "Let's take a breath here. Elena raised a legitimate observation. Charlie, the four were real. Right?"

Charlie (Senior Dev): *softening* "Yeah. They were real. The first one was signature drift — the manifest documented `HT.provide.register(key, fn)` but the runtime called `HT.provide(key, fn)` directly. The smoke harness was calling the runtime shape, and the doc was wrong. We shipped it that way."

Alice (Product Owner): "That's... not great. The manifest is supposed to be the source of truth."

Amelia (Developer): "It is. And the question I want us to wrestle with is: how did the manifest and the runtime diverge in the first place?"

Sanjit (Project Lead): "I can answer that. I wrote the manifest entry first, then I wrote the runtime, and somewhere in between I changed the runtime signature without updating the manifest. They're not auto-generated. There's no compiler to catch the drift. It's a documentation discipline problem."

Dana (QA Engineer): "And the smoke harness didn't catch it because the harness called the runtime, not the manifest. The harness was checking that the runtime matched itself, not that the runtime matched the manifest."

Charlie (Senior Dev): "That's the lesson. The harness should have read the manifest and asserted the runtime against it. If it had, signature drift would have failed at smoke time."

Amelia (Developer): "Okay. So Elena's observation that 'four must-fix items is a lot' — I want to push back gently. What's the alternative? We ship the same story blind, no review, no MUST-FIX findings? What would have been worse?"

Elena (Junior Dev): "I guess... the alternative is shipping the drift into Epic 2 and 3, where every Tool author would have hit it. So yes, catching it now is better. But couldn't we have caught it *during* development instead of in a separate review commit?"

Sanjit (Project Lead): "Yeah. That's the meta-question. The four MUST-FIX items were substantive — signature drift, frozen property descriptors, scanner false positives, brace walker on template literals. Those are real bugs. But they were caught by a *review* step, not by *development-time* checks. If we had a typecheck or a manifest-driven assertion at runtime, we'd have caught them as we wrote them."

Winston (Architect): "Here's the systemic answer. Story 1.14 was implemented via direct file edits — no `bmad-dev-story` red-green-refactor loop. The review was done by the anchored `code-review` skill, two-axis Standards + Spec, instead of `bmad-code-review` which audits against the AC list. The `code-review` skill found the MUST-FIX items. The `bmad-code-review` would have found the *first* one — the signature drift — because that's literally an AC mismatch between the doc and the runtime."

Alice (Product Owner): "And if `bmad-dev-story` had run, the red-green-refactor loop would have surfaced the property descriptor issue when the first failing test asserted `HT.provide = function() {}` should throw."

Charlie (Senior Dev): "Yeah. Honestly — the MUST-FIX items are real, but they shouldn't have made it past `bmad-dev-story`. The fact that they did is a process gap, not a code quality issue."

Amelia (Developer): "So I'm hearing two things. One — the review was substantive and the fixes were real. Two — the workflow trail is missing. The story doc doesn't show what workflow produced it. Future contributors can't tell whether `bmad-dev-story` was used or whether the code was just typed directly."

Sanjit (Project Lead): "Right. And there's a third thing that's uncomfortable to say. Story 1.14 was implemented by me, bypassing the workflow. I had the bash restrictions, so I used `Write` directly. I had the file opens, so I edited. The workflow was available — `bmad-dev-story` is right there in the manifest. I didn't use it because I was moving fast and the story was small relative to the workflow overhead."

Amelia (Developer): "Thank you for naming that. That's the systemic lesson. The workflow overhead is real, but skipping it costs us the review trail. The cost was four MUST-FIX items and a separate review commit. The savings was... what, faster turnaround?"

Sanjit (Project Lead): "Probably not. The review commit `2631cb3` had to be made anyway. The total time was probably the same, just with worse evidence."

Amelia (Developer): "Okay. Let me document this."

**Challenges:**

- 4 MUST-FIX items in Story 1.14 caught post-hoc by review, not during development
- Manifest ↔ runtime signature drift (manifest said `HT.provide.register`, runtime called `HT.provide` directly) — drift would have been caught by a manifest-driven smoke harness
- Smoke harness asserted runtime against itself, not against the manifest — false confidence
- `bmad-dev-story` workflow was bypassed; red-green-refactor loop would have surfaced MUST-FIX #1 and #2 during development
- `bmad-code-review` was bypassed in favor of the anchored `code-review` skill; the bmad equivalent audits against AC list and would have caught the signature drift
- The workflow trail is missing — future contributors can't tell which review ran

### Patterns We Noticed

Amelia (Developer): "Speaking of patterns, I noticed something when reviewing all the story records..."

Amelia (Developer): "Three of the four MUST-FIX items were scanners or regex gates that didn't honor strings, comments, or template literals. The bypass-grep false positive — that was the scanner firing on `localStorage` inside a doc comment. The brace walker on template literals — that was the walker treating `${...}` interpolation as control flow. The unfixed NIT — the smoke harness asserting runtime against itself, similar shape, different domain."

Dana (QA Engineer): "Oh wow, I didn't realize it was that widespread. String-and-comment-aware scanning came up three times in one story?"

Charlie (Senior Dev): "That pattern is going to bite us again. We're going to have more regex gates. Story 4.7 will need an embed-bounds check. The accessibility story will need a regex check for ARIA attributes. Every one of those gates will be a false-positive factory unless the stripper pattern is reused."

Amelia (Developer): "Agreed. The `_code_spans` stripper is ~50 lines of pure-stdlib Python. It should be a reusable pattern, not a one-off. That's an action item."

Amelia (Developer): "Second pattern — fixture-style harness discipline. The vacuous-pass guard on the smoke harness — `pass === 0 && fail === 0 → exit 1` — caught a class of bug where a refactor drops the assertion block. That pattern showed up in `_smoke_site_config.js` too. It's deliberately redundant; the guard fails when the harness is broken."

Alice (Product Owner): "I love that pattern. It's load-bearing. Future smoke harnesses need it."

Amelia (Developer): "Third pattern — the manifest is the source of truth, not the doc. The fact that `assets/js/api-contract.js` got out of sync with `docs/shell-public-api.md` is the same shape as the manifest getting out of sync with the runtime. When the manifest is the contract, harnesses must assert against the manifest. The doc reflects the manifest; the manifest reflects the runtime."

Sanjit (Project Lead): "I want to add — the fact that Story 1.14 had **8** entries in api-contract.js (5 stable + 3 internal) but `HT.useRegistry` was a Middle Man alias we removed during the review — that's a smell. We had two registry entry points for the same data. The `HT.useRegistry` was added 'just in case' a Tool wanted to enumerate providers. We cut it because the `HT.provideRegistry.list()` already covers that use case. Lesson: don't add endpoints for imagined consumers."

Charlie (Senior Dev): "Speculative Generality."

Amelia (Developer): "Right. Speculative Generality. Fowler's smell list."

**Patterns identified:**

1. String/comment-aware scanning is the baseline for any future regex gate (3 of 4 MUST-FIX items in 1.14 were scanner-shape failures)
2. Vacuous-pass guard pattern is load-bearing for any future smoke harness
3. Manifest is the source of truth; harnesses must read the manifest, not their own expectations
4. Speculative Generality: `HT.useRegistry` was a Middle Man alias — should have been caught at design time
