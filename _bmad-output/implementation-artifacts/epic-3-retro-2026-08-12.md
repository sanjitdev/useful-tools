### Patterns We Noticed

Amelia (Developer): "Speaking of patterns, I noticed something when reviewing the twelve story records..."

Amelia (Developer): "Let me name ten patterns I saw across the twelve stories."

**Pattern 1 — Frozen-internal handle.**

Every story that introduced a new surface added a frozen-internal handle: `HT_HISTORY_INIT` (3.6), `HT_HELP_OVERLAY_INIT` (3.3), `HT_GLOBAL_CHORDS_INIT` (3.4), `HT_EXPORT_SCHEMA_VERSION` (3.7), `HT_IMPORT_DIALOG_VERSION` (3.8), `HT_HIGHLIGHT`, `HT_ZIPSTORE` (3.11), `HT_RECENT`, `HT_PINS`, `HT_HOMESIDEBAR` (3.12). The handle is greppable; the implementation can rotate. The best pattern of the epic.

**Pattern 2 — Embed-mode guard.**

`_isEmbed()` predicate + `data-embed-suppressed="1"` marker. Six stories reuse it (3.6, 3.7, 3.8, 3.10, 3.11, 3.12). One tiny predicate, one markup attribute, six use cases.

**Pattern 3 — Vacuous-pass guard.**

Every Node smoke harness has a `pass === 0 && fail === 0 → exit 1` guard. Without it, a smoke that finds nothing to test will pass with 0 assertions, which is worse than failing. The convention caught the 3.12 schema drift on the first run.

**Pattern 4 — Two-pass review = block-the-merge.**

Story 3.6 set the precedent. The pattern didn't hold (pass-2 was post-merge) but the intent is correct. AI-E3-2 means two passes before the merge commit, not one before and one after.

**Pattern 5 — Forward-compat export keys.**

Story 3.7 exported `{version, exportedAt, settings, history, favorites, recent, pins}`. Story 3.12 added `recent` and `pins` AFTER the export feature shipped. The keys were always in the export; the import feature validates them as optional. Zero re-export needed for 3.12 users. That's the api-contract version discipline paying off.

**Pattern 6 — `HISTORY_CAP` hoist (inconsistent).**

Story 3.6 hoisted `const HISTORY_CAP = 50;` per AI-E2-2 (from Epic 2 retro). The cap was previously inline in the function body. Hoisting made it greppable and made the 50-cap behavior testable in isolation. We didn't apply the hoist in 3.7/3.8/3.11/3.12 — only in 3.6. Inconsistency.

**Pattern 7 — Vendored-dependency discipline.**

`highlight.min.js` (200 LOC) and `zip-store.js` (230 LOC) are both vendored into `assets/js/vendor/`. No CDN, no npm, no network at runtime. AD-1 compliant. The decision matrix was: "can we write this in 300 LOC?" If yes, vendored. If no, escalate to Winston.

**Pattern 8 — `--allow-drift` is the recurring tax.**

We now have `--allow-drift index.html` (3.12) and `--allow-drift view-source.html` (3.11). Each one is a manual exemption from the shell-drift check because the page has unique markup. The pattern is "introduce a new chrome surface, add `--allow-drift`, repeat."

**Pattern 9 — `data-print` marker convention introduced but deferred.**

Story 3.10 introduced the `data-print="input|result"` marker convention but the per-tool adoption was deferred to a follow-up. The ACs are met by inheritance (universal chrome-hiding rules already produce clean prints). This is the first story in the epic where we explicitly punted a task. The T4 line in the task list says "deferred to follow-up." That's transparency.

**Pattern 10 — Review-patch commit-message hygiene.**

The review patches commit messages are excellent. `01103fe` (Story 3.5 review) lists six patches with MUST-FIX/SHOULD-FIX/NIT labels. `7b91946` (Story 3.4 review) lists five patches. `f24e4de` (Story 3.3 review) lists 13 patches. The labels make the severity triage readable. We should keep this format.

Sanjit (Project Lead): "Pattern 9 is a teaching moment. The residue-block convention (AI-E3-6) would help here. Story 3.10 is `done` but the T4 deferral is invisible unless you read the file. That's the gap."

Winston (Architect): "The half-life observation: pattern adoption has a half-life. Embed-mode guard was introduced in 3.6 and reused in 3.7/3.8/3.10/3.11/3.12 — five stories of reuse. But the `_isEmbed()` predicate is small enough that it could have been adopted in 3.10 and 3.11 and 3.12 only after we noticed the pattern. The half-life is 'one story.' That's an unreasonably short half-life. The lesson: patterns we adopt should be listed in the architecture spine as 'AD-N+1: pattern-X is canonical for use case Y' so the next story author doesn't have to rediscover it."

**Patterns identified:**

1. **Frozen-internal handle.** Every new surface has a `HT_X_INIT` / `HT_X_VERSION` constant. Greppable, testable, rotatable.
2. **Embed-mode guard.** `_isEmbed()` + `data-embed-suppressed="1"`. Six stories, one pattern, zero bespoke.
3. **Vacuous-pass guard.** `pass === 0 && fail === 0 → exit 1`. Caught 3.12 schema drift on first run.
4. **Two-pass review = block-the-merge.** Pattern intent correct; practice inconsistent on 3.6.
5. **Forward-compat export keys.** Story 3.12 added `recent`/`pins` keys that were always in the export.
6. **`HISTORY_CAP` hoist (inconsistent).** AI-E2-2 applied in 3.6 only; lapsed in 3.7/3.8/3.12.
7. **Vendored-dependency discipline.** <300 LOC? Vendor. >300 LOC? Escalate.
8. **`--allow-drift` is the recurring tax.** Two exemptions now; pattern is "introduce a new chrome surface, add `--allow-drift`, repeat."
9. **`data-print` marker convention.** Introduced in 3.10, per-tool adoption deferred. First explicit punt.
10. **Review-patch commit-message hygiene.** MUST-FIX/SHOULD-FIX/NIT labels in commit messages.

## Critical Insights & Lessons

Amelia (Developer): "Let me summarize before we move to action items."

**Successes:**

- 12 stories shipped; keyboard-first UX is genuinely complete
- API surface stayed frozen across 8 version bumps; all additive, zero breaking changes
- 23 smoke harnesses, 1,400+ assertions; vacuous-pass guards caught the 3.12 schema drift on first run
- Two-pass review on Story 3.6 caught 18 findings that single-pass would have missed
- Embed-mode guard pattern (`_isEmbed()` + `data-embed-suppressed="1"`) reused across 6 stories
- Vendored `highlight.min.js` + `zip-store.js` (430 LOC total) — AD-1 compliant, zero dependencies
- Forward-compat export keys: Story 3.12 added `recent`/`pins` keys that were always in the export

**Challenges:**

- Storage schema drift in Story 3.12: `storage-registry.js` and `chrome.html` inline manifest must stay in sync by convention
- AI-E3-2 follow-through inconsistent on Story 3.6 (pass-2 was post-merge)
- Shell-template byte-aligned gates accumulating (7 gates, 2 `--allow-drift` exemptions)
- Pack pages + `quality.html` manually edited (3.11, 3.12) — invisible in diff
- Status field doesn't communicate residue (3.10 has deferred work; 3.6 has 6-page gate log)
- `HISTORY_CAP` hoist (AI-E2-2) applied in 3.6 only; lapsed in 3.7/3.8/3.12

**Key Insights:**

1. **Forward-only commitments need block-the-merge semantics.** AI-E3-2 was a forward-only commitment; pass-2 was post-merge. The lesson: forward-only commitments must be operationalized as merge gates, not post-merge reviews. AI-E3-9.
2. **Pattern adoption has a half-life.** Patterns we adopt should be listed in the architecture spine as ADs so the next story author doesn't have to rediscover them. Embed-mode guard, frozen-internal handle, vacuous-pass guard, forward-compat export keys, two-pass review, vendored-dependency discipline. AI-E3-10.
3. **`--allow-drift` is the smell, not the solution.** Every exemption is a sign that the byte-aligned gate is too brittle. The flag is correct locally; globally it's a tech-debt ticket. AI-E3-5 (replace byte-aligned gates with structural DOM walk) + AI-E3-11 (tech-debt register).
4. **AI-E1-1, AI-E1-2, AI-E1-4, AI-E3-3 held; AI-E1-3, AI-E2-1, AI-E3-2 partially held; AI-E2-2 has the same one-story-applied-then-lapsed pattern.** The natural curve is to pick up what's load-bearing; the deferred items are still deferred. The lesson: pattern adoption lapse is a class of bug, not a one-off. AI-E3-8 (hoist every cap to a named const at the global level).
5. **Storage schema in two places is the architectural smell.** AD-6 says "storage registry is the single source of truth." We have two sources. The fix is one source (AI-E3-4) — extract to a JSON file and have both consumers import it.
