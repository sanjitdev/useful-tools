# Story 2.9: Existing-Tool Pack Tag Wiring

## User Story

As a future user navigating pack pages (Epic 6),
I want every existing tool to carry the correct `pack` tag (Travel, Finance, Study, Developer, or Household),
So that the pack composition is meaningful and no tool is orphaned.

## Current State (post Story 2.8)

35 tools are promoted with `ready:true`. Every entry already carries a
`pack` array (the Wave-1/Wave-2/Wave-3 promotion scripts emit one).
The schema (`tools.schema.json`) enforces:

- `pack` is an array (minItems: 1, uniqueItems: true)
- each element ∈ {`travel`, `finance`, `study`, `developer`, `household`}

Distribution across the 35 ready:true tools (37 pack-slots, 2 dual-pack):

| Pack | Count | Tools |
|---|---|---|
| household | 12 | age-calculator, animal-race, bmi-calculator, calorie-estimator, color-tools, decision-wheel, eisenhower-matrix, habit-tracker, inflation-calculator*, lifespan-simulator*, pros-cons, space-calculator |
| developer | 9 | base64-codec, json-formatter, markdown-previewer, password-strength, qr-code-generator, random-tools, regex-tester, unit-converter, url-codec |
| study | 7 | gpa-calculator, grade-calculator, lifespan-simulator*, lorem-ipsum, pomodoro-timer, stopwatch, word-counter |
| finance | 6 | bd-tax-calculator, compound-interest, inflation-calculator*, loan-calculator, percentage-calculator, tip-calculator |
| travel | 3 | countdown-to-date, date-difference, world-clock |

(*) dual-pack tool.

All packs already meet the AC's "≥ 3 tools" bar. Schema enum already
rejects unknown pack values. The remaining work is: (a) document the
taxonomy, (b) emit a curated, maintainable pack-tag table that the
auditor and any future tool-bootstrap script can read, (c) add a smoke
that confirms every ready:true tool is in ≥ 1 pack and the totals match.

## Acceptance Criteria

### AC-1 — Pack taxonomy doc

**Given** a maintainer wants to know which pack to assign a new tool to
**When** they read `docs/pack-taxonomy.md`
**Then** they see one paragraph per pack (Travel, Finance, Study,
Developer, Household) with a one-line inclusion criterion and a list of
every tool currently assigned
**And** the doc's tool lists are mechanically generated (no manual
drift).

### AC-2 — `make pack-tags` audit script

**Given** the 35 tools are promoted
**When** the maintainer runs `make pack-tags`
**Then** every tool entry has exactly one `pack` value matching the
curated taxonomy (multi-pack allowed but tracked)
**And** each pack has ≥ 3 tools assigned
**And** the script regenerates `docs/pack-taxonomy.md` from the
canonical `WAVE_*_PACKS` tables in `_promote_wave_*.py`
**And** exits 1 if any tool's pack is not in the taxonomy or if any
pack drops below 3 tools.

### AC-3 — CI rejects missing/invalid pack

**Given** a new tool is added (or an existing tool's pack is changed)
**When** the maintainer runs `make validate`
**Then** the schema validator rejects entries with no `pack` field or
with a value not in the enum (this is already wired — `tools.schema.json`
declares the enum and `validate-tools-json.py` honors it)
**And** a new step `make pack-tags-smoke` runs the static Node smoke
that asserts every ready:true entry has ≥ 1 pack value in the enum.

### AC-4 — Pack-cards ready for Epic 6

**Given** `tools.json` carries pack tags on every ready:true entry
**When** Epic 6's `packs/<slug>.html` pages load
**Then** each page renders the matching tools (`pack.includes(slug)` is
the existing filter — verified at `assets/js/pack-page.js:143`)
**And** the count header (`#pack-page-count`) shows the per-pack total.

### Debug Log

- The first import attempt used `importlib.import_module("scripts._promote_wave_1")`
  which failed because `scripts/` has no `__init__.py`. Switched to
  `importlib.util.spec_from_file_location()` to load each script by file
  path. This is a 5-line change in `load_canonical_roster()` and is the
  correct pattern for the repo's flat `scripts/` layout.
- The WAVE_1 packs were already present in tools.json (set when Story 2.6
  promoted Wave-1) but were never declared as a Python constant — they
  were hand-curated during Wave-1 promotion. Story 2.9 makes the Wave-1
  table explicit in `_promote_wave_1.py` so the auditor can read it.
- Schema already enforces the pack enum (`tools.schema.json` declares
  `enum: [travel, finance, study, developer, household]`), so AC-3's
  "CI rejects missing/invalid pack" is already covered by `make
  validate`. The new `_smoke_pack_tags.js` is a third defense layer
  that catches the failure mode where the schema is bypassed.
- `make validate` confirms every ready:true entry validates against the
  schema (which means the enum check is live in CI). Combined with
  the Python auditor (`make pack-tags` — 35 tools, 37 pack-slots,
  all 5 packs ≥ 3) and the Node smoke (111 PASS, 0 FAIL), the
  pack-tag story has 3 layers of defense: schema, Python auditor,
  Node smoke.
